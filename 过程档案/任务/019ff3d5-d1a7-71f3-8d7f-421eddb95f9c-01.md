## 一、整体结构

```text
原始资料 Word
    ↓
文档解析与图片/公式提取
    ↓
Markdown 教材稿 + 图片资源
    ↓
结构化 JSON
    ↓
知识库 / 题库 / 模型库 / 网页系统
```

目录可以设计成：

```text
physics-library/
├── sources/              # 原始 Word，只读保存
├── chapters/             # 每节知识点 Markdown
├── questions/            # 每道题一个 JSON 或 Markdown
├── solutions/            # 详细答案与解析
├── concepts/             # 知识点、公式、规律
├── models/               # 物理模型
├── assets/               # 图片、公式、示意图
├── indexes/              # 索引文件
└── schemas/              # 数据格式定义
```

- 多栏排版；
- 表格；
- 解析中的推导过程。

```json
  "confidence": 0.91
}
```

建议分为：

- `raw`：原始提取结果；
- `reviewed`：人工确认后的内容；
- `published`：可以用于网页或正式出题的内容。

不要让 AI 直接覆盖原始资料。

我看过了，一轮资料确实和必修、选修资料不太一样，不能完全复用原来的拆分规则。

主要差异有：

1. 一轮资料有两套 Word 体系

- `全书完整的Word版文档`：83 个 Word 文件，偏教师用书、知识讲解和配套精练。
- `另附1套Word版题库`：100 个 Word 文件，偏独立题库，包含自测、例题、变式题和限时练。

2. 题目标记方式不同

必修、选修中常见：

```text
例1
针对训练1
1．
2．
```

一轮题库中则常见：

```text
【自测1】
【例1】
【变式1】
【课时限时练】
```

所以一轮资料需要额外识别“题目类型”和“题目层级”。

3. 内容结构更复杂

一轮主资料通常是：

```text
考点
知识讲解
方法总结
易错辨析
例题
解析
课时精练
```

附加题库通常是：

```text
课程标准
核心素养
自测题
命题点
例题
变式题
课时限时练
答案
解析
```

4. 排版格式也不同

我抽查发现：

- 主资料中的表格较多；
- Word 转 Markdown 后有些表格会变成 HTML 表格；
- 附加题库中有大写 `.DOCX` 扩展名；
- 一轮目录里还有 `.rar`、`.swf`、`.ppsx` 多媒体资源；
- 公式、下划线填空和图片的使用方式也比必修资料更多。

因此，一轮资料建议采用单独的分类字段：

```json
{
  "source_series": "步步高一轮",
  "material_system": "全书完整的Word版文档",
  "content_type": "例题",
  "question_label": "变式题",
  "chapter": "第三章",
  "section": "牛顿运动三定律",
  "question_type": "选择题"
}
```

结论是：一轮资料可以处理，但需要增加一套“一轮专用解析规则”。尤其要重点识别：

- `【自测】`
- `【例题】`
- `【变式题】`
- `课时限时练`
- `命题点`
- `答案`
- `解析`

这样才能准确区分知识讲解、例题、变式题和正式题库题目。

TIF 并不是全面优于 PNG，主要看用途：

| 用途 | 更适合 |
|---|---|
| 原始资料归档、后期编辑、印刷 | TIF |
| Markdown、网页、题库系统、Agent 读取 | PNG |
| 线稿、示意图、表格截图 | PNG |
| 高质量扫描、保留 CMYK 或多页图像 | TIF |

TIF 的优势：

- 可以无损保存；
- 适合印刷和后期图像处理；
- 能保留较多颜色、扫描和排版信息；
- 作为原始素材归档比较稳妥。

PNG 的优势：

- 也是无损格式；
- 浏览器和 Markdown 预览器支持非常好；
- 适合透明背景、公式图、物理示意图；
- 更适合网页、题库和 Agent 使用。

所以最好的方案不是二选一：

```text
TIF：作为原始图片保留
PNG：作为数字化项目的显示和使用版本
```

也就是说，教师用书里的 TIF 不需要删除或替换。后续应该保留：

```text
assets/original/image1.TIF
assets/derived/image1.png
```

Markdown 引用 PNG，JSON 同时记录原始文件和展示文件：

```json
{
  "original": "assets/original/image1.TIF",
  "display": "assets/derived/image1.png"
}
```

这样既保留原始质量，也保证在 Markdown、网页和题库中正常显示。

这很可能不是插件安装问题，而是 TIFF 本身的兼容性问题。你这份教师用书里的 TIF 有多种情况：

- CMYK；
- 黑白灰度；
- 大端/小端；
- LZW 压缩；
- 不同的 TIFF 编码。

VS Code 的 Markdown 预览本质上依赖浏览器渲染，而浏览器对 TIFF 支持很弱，所以即使装了 TIFF Preview，也可能无法正常显示。

最稳妥的办法是：

```text
原始 TIF 保留
    ↓
批量转换为 PNG
    ↓
Markdown 引用 PNG
```

在 macOS 上可以用系统自带的 `sips` 转换：

```bash
sips -s format png image.TIF --out image.png
```

临时查看单张图片，可以用：

- macOS“预览”；
- Finder 空格键快速预览；
- Photoshop、Affinity Photo 或 ImageMagick。

但对于我们的数字化项目，建议统一生成 PNG 展示版。这样 VS Code、网页、Markdown 和后续题库系统都能稳定显示；TIF 仍然作为原始素材保留。

3. 子代理调度有额外成本  
   子代理需要重新加载上下文、分配文件范围、汇总结果。如果任务量不够大，反而会增加管理开销。

4. 当前任务可能没有启用子代理能力

可以加速，但不一定适合把所有图书直接并行处理。

最适合并行的情况是：

- 每本书目录相互独立；
- 转换规则已经确定；
- 子代理只写自己的输出目录；
- 最后由主代理统一合并索引和验收。

推荐结构：

```text
主代理
├── 子代理：图书 A
├── 子代理：图书 B
├── 子代理：图书 C
└── 主代理统一检查格式、图片、公式和台账
```

这样可以缩短等待时间，尤其是多本书都需要独立 OCR、Markdown 转换和图片提取时。

但有几个限制：

- 子代理不能同时修改同一个总台账；
- 每本书格式差异大时，先要用主代理确定规则；
- 需要给每个子代理清晰的目录边界；
- 最终仍需要主代理统一检查，不能简单拼接结果；
- 如果转换主要由本地脚本完成，瓶颈可能是磁盘、OCR 或 CPU，并行过多反而变慢。

所以更合理的策略是：

1. 主代理先处理 1 本书，确定转换规范；
2. 用 2–4 个子代理并行处理其他图书；
3. 每个子代理输出独立结果和日志；
4. 主代理统一合并索引、检查质量和补漏。

你可以让当前 Luna 任务明确尝试并行：

> 目前有多本相互独立的图书，请先评估是否适合拆分为 2–4 个子代理并行处理。主代理负责统一格式规范、任务分配、中央台账和最终验收；每个子代理只处理指定图书并写入独立输出目录，不修改共享索引。先完成一个小规模并行试点，再决定是否扩大并发数。
