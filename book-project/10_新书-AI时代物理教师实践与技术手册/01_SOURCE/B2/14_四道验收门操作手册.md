# 四道验收门操作手册

> 状态：作者已确认采用“四道验收门”，本文件将其从概念框架展开为可执行规程。  
> 适用对象：教师与Agent协作开发的物理网页、模拟实验、数据处理页、题目资源、课程网站及相邻数字资源。  
> 定位：这是写作与实践准备稿，不是已经经过大样本验证的量表；正式出版前需用至少2—3类项目继续试用、删改和定标。

## 一、四道门到底是什么

四道门不是项目结束时一起打勾的清单，而是四种独立的否决权：

| 门 | 它有权否决什么 | 最终签字人 |
| --- | --- | --- |
| 运行门 | “这个交付物能够在指定环境完成指定操作” | 项目执行者；教师确认真实使用路径 |
| 物理门 | “对象、模型、公式、单位、趋势和数据身份正确” | 物理教师 |
| 教学门 | “学生能够按设计完成有意义的学习行动” | 任课教师／教研者 |
| 发布门 | “可以按当前证据、权限和维护条件对外提供” | 作者／项目负责人 |

任何一门都不能被另一门替代：

- 构建成功不能证明物理正确；
- 物理计算正确不能证明学生能看懂、会操作；
- 课堂上用过不能自动证明学习有效；
- 本地验收通过不能自动获得对外发布权限。

## 二、每道门只有四种结论

| 结论 | 含义 | 下一步 |
| --- | --- | --- |
| **通过** | 本门硬条件全部有证据，剩余问题不影响当前用途 | 进入下一门或形成可用版本 |
| **退回** | 问题已定位，能够通过修改再次验收 | 写退回理由、责任人和复验项目；修改后重走受影响的门 |
| **暂停待确认** | 缺少原始数据、器材身份、课堂事实、授权或作者决策 | 不猜、不补写；列出所需材料与确认人 |
| **停止** | 触及隐私、版权、危险操作、核心模型不成立或无法恢复 | 停止发布或停止该功能；保留现场与原因 |

“部分通过”不作为含混的第五种结论。若只适合本地演示，就写清“本地演示通过、公开发布未通过”；若只核了三个输入样例，就写“指定样例通过”，不写“物理门通过”。

## 三、开门以前先冻结五样东西

没有冻结对象，验收很容易变成“Agent做了A，却拿B来证明”。开工前至少保存：

1. **任务Brief**：解决谁的什么问题，首版交付什么，当前不做什么；
2. **输入清单**：原始数据、图片、器材资料、公式和课堂材料的准确路径与版本；
3. **目标对象**：要验收的文件、页面、网址、分支、版本号或提交标识；
4. **验收样例**：正常、边界、异常和独立手算样例；
5. **可恢复基线**：修改前的副本或版本节点，以及恢复方法。

推荐建立一个最小证据包：

```text
review/<日期-任务名>/
├── 00-任务与边界.md
├── 01-运行记录.md
├── 02-物理模型与样例.md
├── 03-教学路径走查.md
├── 04-发布检查.md
├── assets/            # 截图、导出文件、必要照片
└── verdict.md         # 四门结论、退回和签字
```

这不是要求教师做复杂文档工程。小项目可以合并成一个Markdown文件，但五类证据不能只剩Agent最后的总结。

## 四、整套验收怎样运行

```text
冻结任务与基线
→ Agent实现一个最小改动
→ Agent自检并提交文件差异、命令结果和已知限制
→ 运行门
→ 物理门
→ 教学门
→ 发布门
→ 保存可用版本与退回记录
```

它是一个会回头的流程：

- 物理门要求修改公式，修改后必须重新过运行门；
- 教学门要求删除自动排序或新增提示，修改后要重过运行门和物理门；
- 发布门发现图片无授权，换图后至少重过运行门和教学门；
- 任何门发现验收对象不是当前真实页面，四门记录全部作废，重新锁定对象。

## 五、运行门：证明“这一份真的能用”

### 1. 进入条件

- 已指定准确的文件、页面、网址、分支或版本；
- 知道它应在哪种设备、浏览器、网络和账号条件下运行；
- 有一条真实核心路径，而不只是首页能打开。

### 2. 谁做什么

- Agent：运行构建、测试和检查命令，逐项操作核心路径，保留原始输出；
- 独立检查者：按冻结任务重跑，不复用生成者的“我已经测过”；
- 教师：确认检查的是课堂实际会使用的入口、设备和步骤。

### 3. 具体操作

#### 步骤R1　锁定验收对象

记录：

- 本地文件路径或线上URL；
- 当前分支／提交／版本时间；
- 服务地址和端口；
- 浏览器与设备；
- 是否依赖网络、账号、蓝牙、串口或外部API。

**硬规则**：替身服务器、另一个端口、旧构建产物、仅源码预览，都不能证明目标页面可用。DeepSeek事故材料中“新端口返回200”却未验证用户实际页面，是本门必须防住的典型错误。

#### 步骤R2　从干净状态启动

- 按项目规定安装或确认依赖；
- 清楚使用当前源码而非旧缓存／旧构建；
- 启动项目，记录实际地址；
- 若是静态文件，记录打开方式与必要资源；
- 若需要外设，记录设备连接前提和无设备时的表现。

#### 步骤R3　运行项目已有检查

按项目规则运行构建、类型检查、测试、链接检查或数据校验。记录原始命令、退出状态、时间和完整结论。

**禁止写法**：“AI说测试通过。”  
**合格写法**：“2026-08-30在提交`xxx`上运行`npm run build`与`npm test`，退出状态为0；完整记录见附件。该结果只证明本次本地构建和既有测试通过。”

#### 步骤R4　走完一条真实核心路径

以学生或教师的实际顺序完成：

```text
进入准确页面
→ 输入或选择真实任务数据
→ 触发主要操作
→ 查看反馈／图表／计算
→ 导出、清空或重新开始
```

每一步记录预期、实见和证据。页面返回200、构建成功或按钮存在，都不能代替整条路径。

#### 步骤R5　至少检查四类边界

1. 空输入或漏填；
2. 零值、负值或边界值；
3. 小数、单位、中文字符、复制粘贴等真实输入；
4. 断网、外部资源失效、无设备、重复点击或刷新。

边界样例由任务决定，不机械要求每项都测。例如完全离线的静态图无需测账号，但必须检查图片和字体是否依赖外网。

#### 步骤R6　核对本地、冻结版与线上边界

- 本地通过，只写本地通过；
- 冻结副本通过，只写冻结副本通过；
- 线上页面需在部署后重新核对准确URL、资源和缓存；
- 未经发布门批准，不把本地结果写成“已上线”。

### 4. 必备证据

- 目标对象标识；
- 构建／测试原始结果；
- 核心路径记录；
- 边界样例表；
- 关键截图或导出文件；
- 已知限制。

### 5. 通过、退回、停止

**通过**：目标对象明确；项目检查通过或失败已证明与当前交付无关；真实核心路径完成；关键边界有结果；没有隐藏的致命依赖。  
**退回**：按钮、链接、计算触发、导出、重置、路由、资源或设备路径出错；能定位并修复。  
**暂停**：没有目标地址、无法确定当前版本、真实设备不可得且设备是核心前提。  
**停止**：需要使用未授权账号／密钥，或运行会造成不可恢复的系统、数据或设备风险。

## 六、物理门：证明“它表达的是这个物理过程”

### 1. 进入条件

- 运行门至少在当前冻结版本通过；
- 已有页面字段—物理量—实物对象映射；
- 已说明模型用途和不覆盖的真实因素。

### 2. 先写一张物理模型卡

| 项目 | 必填内容 |
| --- | --- |
| 研究对象 | 页面中的每个量对应什么物体、装置或过程 |
| 系统边界 | 哪些物体属于系统，哪些作用来自外界 |
| 时间／空间区间 | 比较的是哪两个时刻、哪段位移或哪一区域 |
| 假设与忽略 | 摩擦、空气阻力、转动、传感器延迟等怎样处理 |
| 变量与单位 | 符号、输入单位、内部换算、显示单位 |
| 核心关系 | 公式、方向、正负号、坐标约定、守恒或近似条件 |
| 数据身份 | 实测、手动录入、模拟、默认、修正和派生数据怎样区分 |
| 适用边界 | 哪些参数或情境下不再可靠 |

这张卡先于代码解释。若连教师都无法写清研究对象和系统边界，不应让Agent继续把公式包装成更漂亮的界面。

### 3. 具体操作

#### 步骤P1　逐字段对回真实对象

- 字段名是否对应正确器材和测量量；
- 图片是否为同一种装置、同一状态；
- `v₁/v₂`、初态／末态、左／右、正／负是否由位置和时序定义，而非由数值大小自动定义；
- 原始记录是否被后台排序、平滑、补全或替换。

任何自动变换都要可见，并保留原始值。数据“更好看”不构成修正理由。

#### 步骤P2　核对单位和量纲

- 输入单位与公式内部单位是否一致；
- 克、千克，厘米、米，毫秒、秒等换算是否明确；
- 结果单位是否正确；
- 图轴、表头、导出文件和页面说明是否使用同一口径。

#### 步骤P3　准备五类样例

| 样例 | 目的 | 例子 |
| --- | --- | --- |
| 标准点 | 验证常见过程 | 一组正常实验记录 |
| 零点／边界点 | 查公式与程序边界 | 位移为0、速度相等、频率为0 |
| 极端点 | 查趋势和数值稳定 | 很大／很小参数、接近临界值 |
| 反预期点 | 检查页面是否篡改异常 | `v₁>v₂`仍保留原顺序 |
| 独立基准点 | 与程序外计算比较 | 教师手算、电子表格或另一独立脚本复算 |

不要求每个项目机械使用同样数量，但必须同时包含正常、边界、异常和独立基准四种思路。

#### 步骤P4　检查不变量、趋势和极限

根据模型选择：

- 量纲是否一致；
- 守恒量是否在适用条件下保持；
- 参数增大时趋势方向是否正确；
- 对称点、零点、转折点和极限状态是否符合物理；
- 数值离散、采样和动画是否制造假象；
- 图像与公式表达的是不是同一个量。

#### 步骤P5　把程序结果与独立证据比较

独立证据不能只是让同一个Agent再次解释自己的代码。可选证据：

- 教师手算；
- 原始实验记录；
- 教材／权威公式；
- 另一种实现或电子表格复算；
- 实物测量与页面输出对照；
- 没参与实现的物理教师审读。

#### 步骤P6　写清“正确到哪里”

示例：

> 冻结页面在五组指定输入下保留原始次序，单位换算与当前公式的独立复算一致。尚未验证自动采集、所有浏览器和真实系统中未建模能量的大小。

### 4. 必备证据

- 物理模型卡；
- 字段—对象—单位表；
- 样例输入、预期、实见和差异；
- 独立计算或原始记录；
- 适用边界与未建模因素。

### 5. 通过、退回、停止

**通过**：对象、系统、单位、公式、方向和数据身份明确；正常、边界、异常与独立基准不冲突；边界已写清。  
**退回**：标签、单位、公式、图轴、符号、趋势或数据处理可修正；修正后重过运行门。  
**暂停**：器材身份、原始数据、公式口径或课堂时序无来源可核。  
**停止**：核心模型与任务对象不一致，或系统会把模拟、默认、AI补全数据冒充实测数据。

## 七、教学门：证明“学生做的是有意义的学习行动”

### 1. 进入条件

- 运行门和物理门已通过当前版本；
- 已写明目标学生、学习目标和具体学习摩擦；
- 已有一条不用开发者现场救场的学生路径。

### 2. 具体操作

#### 步骤T1　把功能翻译成学生动作

不要写“页面提供动画、图表和AI提示”，改写为：

- 学生先观察什么；
- 学生要预测或输入什么；
- 学生改变哪个量；
- 学生比较哪两种结果；
- 学生用什么证据解释；
- 教师在哪一步追问或收束。

若一个功能无法对应任何学生动作或教师决策，它可能只是装饰。

#### 步骤T2　从学生入口完整走查

以目标设备和课堂网络，从学生第一次看到页面开始，不使用开发者知道的隐藏路径：

1. 能否看懂任务和字段；
2. 能否独立完成输入、操作和重置；
3. 出错后是否知道怎样修正；
4. 页面反馈是否直接给掉结论、替学生做了关键判断；
5. 导出、投屏或小组汇报是否与课堂流程衔接。

#### 步骤T3　检查技术动作是否改写了教学任务

重点问：

- 自动排序是否拿走了异常判断；
- 一键模拟是否绕过真实测量；
- 自动提示是否直接泄露推理结论；
- 动画是否让学生只看热闹而不作比较；
- 默认数据是否被误当成本组实验结果；
- “修正”功能是否让原始证据消失。

#### 步骤T4　检查课堂约束

- 每组设备数量和学生操作机会；
- 网络、账号、蓝牙／串口、投屏和浏览器条件；
- 一次课可用时间；
- 教师是否能在30秒内判断页面当前状态；
- 字号、对比度、触控区域和大屏可读性；
- 页面失败时是否有纸笔、实物或旧版本替代方案。

#### 步骤T5　区分四级教学证据

| 证据级别 | 允许表述 | 不允许越界 |
| --- | --- | --- |
| 设计走查 | “设计用于……”“教师走查通过指定路径” | 不写学生已经会用 |
| 小范围试用 | “在若干教师／学生试用中发现……” | 不写普遍适用 |
| 真实课堂使用 | “在某次课堂中进入了某环节” | 不自动写学习效果 |
| 效果证据 | “在明确样本、工具和比较下出现……” | 不超出数据与设计 |

教学门通过的是“当前用途下的教学可用性”，不是自动获得最高证据级别。

#### 步骤T6　写出教师保留的控制点

- 哪一步必须由教师确认；
- 哪一类异常不能自动修正；
- 哪个结果只作为讨论材料；
- 什么时候停止使用页面，回到实物、板书或纸笔；
- 学生反馈怎样进入下一版本。

### 3. 必备证据

- 教学难点—功能—学生动作对照；
- 学生路径走查记录；
- 课堂设备和时间条件；
- 失败替代方案；
- 当前证据等级和禁说项。

### 4. 通过、退回、停止

**通过**：目标学习行动明确；学生路径可完成；关键判断未被自动功能拿走；课堂条件匹配；教师控制点和证据等级写清。  
**退回**：字段、反馈、步骤、认知负荷、设备适配或课堂时长不合适；能通过删减或调整修复。  
**暂停**：需要真实课堂或目标读者试用才能判断，当前只有设计意图。  
**停止**：页面诱导错误概念、冒充诊断、自动替学生完成核心学习任务，或没有安全可行的课堂使用条件。

## 八、发布门：证明“这一版可以对这一群人公开”

### 1. 进入条件

- 前三门在准备发布的准确版本上通过；
- 已确定发布对象、访问范围和维护负责人；
- 已有可回滚版本。

### 2. 具体操作

#### 步骤L1　核对素材来源和权利

逐项登记：文字、图片、学生作品、课堂照片、视频、音频、代码、字体、数据和第三方库的来源、作者、许可、署名和可公开范围。没有来源的素材不能因“网上能找到”就直接发布。

#### 步骤L2　处理隐私和身份

- 学生姓名、学号、班级、头像、对话和作品是否脱敏；
- 是否有肖像、作品与课堂材料授权；
- 公开页是否能反推出真实身份；
- 审阅数据与公开数据是否物理隔离；
- 私密记忆、账号、邮箱、网盘和本地文件是否被带入发布包。

#### 步骤L3　检查权限、密钥与外发路径

- 代码和静态文件中是否含API Key、Token、服务器地址或本地绝对路径；
- 页面会向哪些域名发送数据；
- 第三方脚本、CDN、统计和表单收集什么；
- 后台、部署账号和自动任务是否使用最小权限；
- 第三方Skill、插件和连接器是否真正需要进入发布流程。

#### 步骤L4　建立主张—证据边界

| 主张 | 至少需要的证据 |
| --- | --- |
| 页面存在／本地可运行 | 当前版本文件＋本地运行记录 |
| 线上可访问 | 发布后准确URL核对 |
| 进入课堂某环节 | 学案、课堂记录或多源互证 |
| 改善理解／成绩／效率 | 明确样本、工具、过程和分析 |

“测试通过”“教师觉得好用”“学生很喜欢”不能自动升级为学习效果。

#### 步骤L5　锁定发布版本与回滚

记录：

- 发布版本／提交／构建时间；
- 部署目标和公开URL；
- 发布前完整检查；
- 回滚到哪个版本、由谁执行、怎样确认回滚成功；
- 缓存、CDN、数据库或外部服务怎样同步恢复。

#### 步骤L6　明确维护责任和停止条件

- 谁负责发现链接、依赖、浏览器和内容过期；
- 多久检查一次；
- 用户怎样报告问题；
- 出现物理错误、隐私投诉、授权撤回或服务异常时，谁有权下线；
- 无人维护时，是保留冻结说明、转为本地资源，还是撤下。

#### 步骤L7　发布后从外部重新验收

不要用开发者已登录、已缓存的环境作为唯一证据。使用普通访问者路径检查：

- 域名、HTTPS、路由和资源；
- 核心操作；
- 移动端／课堂大屏中实际需要的显示；
- 公开页面不含私密内容；
- 版本号、更新时间、反馈入口和必要边界说明。

### 3. 必备证据

- 素材与授权台账；
- 隐私脱敏记录；
- 外部依赖、权限和数据流清单；
- 主张—证据表；
- 发布版本、URL和回滚卡；
- 维护负责人和下线条件。

### 4. 通过、退回、停止

**通过**：来源、隐私、权限、主张、版本、回滚和维护责任清楚；发布后准确URL复验通过。  
**退回**：署名、说明、依赖、路由、访问范围或版本记录可补齐。  
**暂停**：授权、账号、部署范围、证据表述或维护责任未确认。  
**停止**：存在学生身份泄露、无授权素材、公开密钥、无法回滚的高风险发布或核心物理错误。

## 九、小项目与高风险项目采用不同强度

### 最小版：本地单页／教师自用原型

至少完成：

1. 锁定文件和版本；
2. 跑通核心路径；
3. 检查正常、边界、反预期与独立基准；
4. 写清学生动作和当前不做；
5. 不含真实学生隐私与密钥；
6. 保存可恢复版本；
7. 明确“仅本地原型，未证明课堂效果”。

### 完整版：公开网站／学生数据／设备控制／自动任务

除最小版外，必须增加：

- 多设备或真实设备验证；
- 权限与数据流审查；
- 素材授权和隐私台账；
- 独立物理审读或复算；
- 发布后外部路径复验；
- 负责人、告警、预算、重试和停用；
- 版本回滚演练；
- 真实课堂或目标读者试用达到相应主张所需证据。

风险越高，门不是越多，而是每一道门需要更强的证据。

## 十、哪些检查交给机器，哪些必须留给人

| 检查 | 适合自动强制 | 必须由人判断 |
| --- | --- | --- |
| 构建、类型、链接、数据格式、文件缺失 | 是，可写成脚本、测试或Hook | 判断失败是否影响当前用途 |
| 单位换算、固定样例、守恒量、边界值 | 可自动复算一部分 | 模型边界、器材身份、异常是否应保留 |
| 字段完整、步骤是否可点击、对比度 | 可自动发现一部分 | 学生是否理解任务、反馈是否拿走思考 |
| 姓名模式、密钥模式、缺少署名、未登记素材 | 可自动扫描 | 授权范围、主张强度、是否适合公开 |
| “改动是否平凡”“是否值得写入Skill” | 不宜完全自动 | 教师／作者判断 |

可机械判断的项目，应尽量从文档提醒升级为脚本、测试或Hook；依赖语义和专业判断的项目，应保留明确签字，而不是制造表面自动化。

## 十一、一条合格的“完成声明”长什么样

不合格：

> 页面已全部完成，测试通过，物理正确，可以上线。

合格：

> 冻结版本`X`已在本地地址`Y`完成构建、既有测试和学生核心路径走查；四组指定样例与独立复算一致，反预期输入保持原始次序。当前只通过本地运行门和指定模型的物理门。真实课堂使用、图片授权和线上部署尚未核验，因此教学门处于“设计走查通过”，发布门暂停。

完成声明的价值不在于显得谨慎，而在于让下一位教师知道：现在可以做什么、还不能说什么、下一步缺什么。
