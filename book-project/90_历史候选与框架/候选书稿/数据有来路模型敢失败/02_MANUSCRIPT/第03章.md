# 第3章　三十六个学生同时动手

科创选修课的教室里，点名录上是三十六个名字，分成八个组；每组一块平板、两块ESP32开发板，桌上还散着舵机、超声波模块、称重传感器和几卷杜邦线。课程要做的项目很朴素：让每个组用积木式的编程，把一块板变成走廊灯、电子秤、倒计时器或者一盏会变颜色的灯。

真正难的事情在项目之外：三十六个学生要同时动手。八个组在同一节课里各自改程序、各自下发、各自看到自己板子的反应，还要互不干扰。我们试过把现成的平台直接搬进这间教室，三个学期下来，被磨出三个痛点——这三个痛点最终促使我们自己做了整个平台。这一章讲的就是这次开发：它要解决的问题、它做的每一处取舍，以及它还欠着的账。

## 一、选修课的实情走在平台设计前面

先把痛点摆出来，因为整个系统的每一处设计都能追溯到它们。

第一个痛点，平板装不了开发环境。学校配发的平板安装不了传统桌面开发工具，浏览器里也跑不起完整的离线工具链；要给几十台平板逐台装应用，安装差异和维护成本在班级授课里无法接受。第二个痛点，编译排队。以C++工具链烧录的方案，一组学生"修改—编译—烧录—运行"一轮要等编译器；八个组同时来，编译任务在教师机上排起队，课堂节奏在等待里散掉。第三个痛点，连线管理。USB线逐台连接的方式在小组间传递时既慢又易错，学生的代码、设备与人三样东西对不上号，一节课的后半段常常在排查"谁把谁的板子刷了"。

三个痛点指向同一个根源：现成平台把"一个学生的个人创作"当作设计原点，一间教室需要的是"全班并发"的调度。前者优化的是单人体验的流畅，后者要解决的是几十路同时开工时互不踩踏——这是两种不同的工程。

## 二、市面上的平台，多为一人一板而生

说"现成平台不够用"，要先承认现成平台走到哪一步了。信息技术课程标准已把开源硬件项目设计纳入课程内容；《中小学实验教学基本目录》对跨学科与项目式实践有明确要求。实践层面，Mixly由师范团队持续建设，支持ESP32与MicroPython；掌控板与mPython、Mind+构成中小学开源硬件的主流选择。同行们用这套生态做出了很多好东西：有人用掌控板改造法拉第电磁感应定律实验，打通了这一路线与物理教学的接口；有人开发了基于掌控板的高中人工智能校本课程；有人在智慧课堂里实践Blockly编程教学；还有人把开源硬件用到生物学性状分离比的模拟实验里，项目式组织模式也有成熟的范例。

我们逐一翻检了2018年以来这一族的文献，发现它们的共同点：面向一个学生的个人创作场景——一块板、一台终端、一位作者。这些工作没有错，只是场景与我们的教室差一个数量级。把三十六人的并发当作设计前提的平台，在我们的检索范围内还没有见到。与其在别人的原点上打补丁，我们决定把原点挪过来：为一间教室做一次设计。

## 三、平板、服务器、开发板各管一段

系统的名字叫ESP32Blockly，由三端构成，每一端只管一段事。

学生端是平板浏览器里的渐进式网页应用。学生用Google Blockly拼搭积木，页面实时生成MicroPython代码，点上传就送到设备。教师在学生端看不到"安装"这个动作——打开网页，干活，关掉走人。教师端是运行在教师机上的中央服务器：托管学生端页面，维护一张"设备编号—连接"注册表，按设备编号把各组代码路由下发到对应的ESP32；旁边配一个教师管理台，呈现全班设备的在线状态与下发情况。设备端是刷入MicroPython的ESP32：开机连上WiFi后向服务器注册，收到代码即写入运行，串口输出实时回传到学生端的控制台——板子跑成什么样，学生当场看见。

传输层备了三条路。WiFi模式走上述链路，支持多组并发，是现网的默认用法；有线USB模式用Web Serial经浏览器直连ESP32，完成MicroPython读写与固件烧录，留给无WiFi的教室和设备初始化；蓝牙模式用Web Bluetooth直连，是无WiFi场景的简化备选。眼熟的读者会认出来：后两条路与上一章的网页版DIS是同一族浏览器直连技术。在编程平台里，直连是救急通道，路由才是日常——采集要的是点对点的灵活，下发要的是全班并发的秩序。

## 四、八类积木按物理量认亲

积木是学生看见的全部。按颜色分八类、三十余块：引脚IO管板载LED、数字读写与PWM；时间管循环与延时；传感器类管模拟读、按钮、DHT温湿度、超声波测距、HX711称重、旋转编码器；显示类管OLED与四位数码管；网络类管HTTP获取、JSON解析与MQTT发布；串口管打印回显；执行器管蜂鸣器、舵机、继电器与电机；RGB类管三色灯与WS2812彩灯。

分类的内在逻辑是物理量，也是物理教师的私心。距离、力、温湿度、角度，恰好是物理实验最常用的几个量——同一块ESP32，既能撑起科创项目的智能小装置，也能随时转去承担实验数据采集。项目里还带着phyphox的蓝牙库，ESP32采到的物理数据可以直接传到手机phyphox做力学与运动学分析。选修课搭的这副骨架，与物理课的血缘是通的。

**表3-1　八类积木与它们认的物理量**

| 类别 | 代表积木 | 物理量／用途 |
|---|---|---|
| 引脚IO | 板载LED、数字读写、PWM与占空比滑条 | 电平与输出的基本动作 |
| 时间 | 一直重复（循环）、延时 | 时序控制 |
| 传感器 | 模拟读、按钮、DHT温湿度、超声波测距、HX711称重、旋转编码器 | 温度、湿度、距离、力、角度 |
| 显示 | OLED清屏与文字、四位数码管、I2C扫描 | 读数的呈现 |
| 网络 | HTTP获取、JSON解析、MQTT发布 | 数据的进出（连接权限不开放） |
| 串口 | 串口打印、带标签打印 | 调试回显 |
| 执行器 | 蜂鸣器、舵机转角、继电器、电机、角度盘 | 动作输出 |
| RGB | 三色灯、WS2812彩灯 | 状态的可视指示 |

这张表里最能说明设计取向的是传感器一列：DHT给温度湿度，超声波给距离，HX711给力，编码器给角度——四个传感器，四个物理实验的常客。学生拼过"称重报警器"的积木，再进物理实验室看见力传感器，两块牌子后面是同一类东西：把物理量变成电信号的换能器。选修课与物理课之间的那扇门，就这样被四块积木悄悄推开。

## 五、设备编号：并发的秩序与隐私的边界

全班并发最要紧的一件小事，是"谁的代码到谁的板"。答案朴素得过分：每块ESP32以固定编号登记，如G3-2；学生上传前在界面上选择本组编号，服务器只把代码发给该编号的设备。一组修改代码，别组设备纹丝不动。绑定只有编号，没有密钥——课堂要的是快与不出错，配对流程能省则省，安全边界由教室的物理空间和教师管理台兜底。

有两处"不开放"同样要紧。一处是WiFi连接积木不对学生开放：网络类积木给了HTTP、JSON、MQTT，唯独不给连接与断开WiFi的积木——一次误触断网，全班的设备集体掉线，这类权限收在设备端固件与教师手里。另一处是学生代码不在服务器落盘：服务器只做转发与状态记录，不保存学生代码正文，学生姓名不进系统。这既是隐私红线，也顺手简化了管理——下课即清空，教师无需维护任何学生数据。设备编号只对应板子，从设计上就不存在"学生行为档案"这种东西。

还有一段实现要如实交代。学校平板的浏览器对Web Serial与Web Bluetooth的支持不完整，为此另备了一个安卓原生壳，把网页应用装进壳里、用原生桥补齐直连能力——这段描述是从构建产物与测试类名推断的，安卓端源码尚未入库，细节以补齐源码后的核实为准。WiFi路由模式不受此限制，这也是它被设为默认模式的原因之一。

## 六、每块板都有一页病历

十六块板每周被几十个学生轮流使用，坏是常态，关键是坏了之后多快能归队。项目里维护着一份硬件台账，每块板一页记录：编号、测试结果、出过的故障、复测的结论。配套一份批量健康测试的方法——一批板子统一过一遍检查项，合格的回教室，不合格的进台账等候处理。设备身份另有一份MAC地址与别名的映射表，编号背后的机器身份也有账可查。

## 七、三周四十三次提交

这套系统的开发记录，是一条再干净不过的时间线：2026年6月15日首次提交，到7月5日共四十三次提交，约三周高度集中的开发，单人完成。网页端是原生HTML、CSS与JS，没有前端框架；服务器是Node加WebSocket；固件是MicroPython——每一层都选了最薄的技术，没有一个为了简历好看而引入的组件。

三周从零到全班可用，靠的当然是AI辅助开发，但工具与方法都在另一章详细交代，这里只留一个观察：单人教师在这三周里扮演了产品经理、程序员、测试员与电工四个角色，每晚提交之后，第二天拿到教室里真机检验——这种开发节奏只有在"开发者就坐在用户隔壁教室"时才可能。界面沿用数智育才门户的"育才蓝"设计系统，安装包名与设备二维码都指向shuzhiyucai.cn，规划中的整合方案已经写进项目文档：编程、采集与实验资源，将来进同一个门。

## 八、从四十二个例程到一本校本教材

平台之外是课程内容。例程库内置三篇共四十二个例程：第一篇启蒙积木编程，第1到7章，纯积木，从点亮板载LED到眨眼到呼吸灯；第二篇进阶MicroPython，半积木半代码，学生开始看见积木背后的文字；第三篇联网物联网，HTTP、JSON、MQTT，板子开始与世界对话。配套的校本教材《从积木到智能体——ESP32智能硬件创意编程》把例程组织成课程，梯度是从运行范例、修改积木，到自主设计一个智能小装置。

例程不是纸上谈兵。项目自带一个脚本，用浏览器把教材十三章的代表性例程实时渲染成积木工作区截图，共三十六张——每一张都是真实运行界面的留影，拿来就能当教材插图与课堂投屏。这一批截图也成为本书配图的直接来源。

## 九、并发课堂还欠一本数据账

系统完成了开发、通过了真机测试，课堂按这套架构组织——到这里为止，记录是完整的。再往前一步的证据还在积累：一学期下来各例程的下发次数、各组完成率、学生作品清单，这些数据系统都能留下痕迹，但还没有整理成账；课堂照片与应用实录也待归档。所以在这一章里，读者看不到任何"提升了兴趣""效率提高了百分之多少"的说法——账没记完，话不说满。边界的另一侧也如实交代：教师机是单点运行，适合单教室场景，跨教室并发要另行部署；MicroPython解释执行，对付不了高刷新率的控制循环。

课程方案要求学生"运用信息技术优化物理实验"，同行的低成本传感器工作都指向同一个方向：开源硬件正在成为物理实验的技术底座。这一章为这个方向补上的一层是课堂调度——让一个班的并发使用成为平台的设计前提。至于它跑起来到底什么样，等2026年秋季学期的数据账记完，我们再来续写。

电子平台的履历短而清楚：三周、四十三次提交、一条git时间线。下一章的物件年纪更长，履历也更曲折——一件教具从获奖、申请专利到收到驳回通知，四次身份变换，每一步都留下了文书。
